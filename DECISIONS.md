Choices made while setting up the project, with the reason and how to change each one.

| 18 | **OpenClaw keeps Tool Search on, and the builders' first backup is `nemotron-3-ultra`** (was `gemini-2.5-flash`) | `gpt-oss:120b` sometimes writes its tool call as text instead of running it. Measured on 2026-10-14: right 7 of 9 times with Tool Search on, 2 of 8 with it off, so it stays on (the 7-tool limit still cuts the prompt from 46.8k to 31.3k chars). `nemotron-3-ultra` got the same task right 3 of 3 times, so the retry after a glitch runs on it. It is NVIDIA, so builders on a backup still never share the reviewer's family (Google) | `agents/openclaw/openclaw.json5` |
| 19 | **When all of an agent's models are rate-limited, only that agent pauses, and the human gets a ticket.** The dispatcher skips it for 15, 30, 60, then at most 120 minutes between tries; the other agents keep working. It files one `rate-limit` + `needs-human` issue, comments on each further try, and closes it when the agent runs again. The item it was on keeps its labels, and no failure is counted | A rate limit isn't the ticket's fault. Before this, two rate-limited runs parked the ticket as `needs-human`, and every other agent on the same provider was parked one by one. Pausing per agent, not per provider, needs no knowledge of how each provider counts its limits. Only the runtime's own error is read (OpenClaw's last model-attempt line, Hermes's result record), never tool output, because the app's Run now has a rate limit and its code and tests mention 429. Tested on 7 sample errors on 2026-10-14. Rule 6 (one open ticket per builder) still holds: a builder whose PR waits for a paused tester doesn't start a second ticket | `ops/dispatcher.sh` (rate limits section) |
| 20 | **Send-backs are counted per check: CI, test and review each allow 2, and the third by the same check goes to the human. A red CI is re-run once per commit before it counts** | One shared count of 3 let a flaky CI failure use up the budget that a reviewer's "this isn't what the ticket asked for" needs. The dispatcher counts each send-back as it happens: its own for CI, and a tester or reviewer run that leaves its PR at `changes-requested` (they are only woken on `needs-test` or `needs-review` PRs, so the label is theirs). All agents share one GitHub account, so the PR timeline can't tell who added the label. At most 6 fix runs per PR before a human looks | `ops/dispatcher.sh` (send-back counting), counts in `~/work/.dispatcher/sendbacks/` on the VM |
| 21 | **A new lesson reaches every agent on its next wake-up, before the human reviews it.** The dispatcher adds `Lesson:` lines posted since the last merged `lessons` PR (the newest 10, minus those already in `LESSONS.md`) to all six agents' wake-up messages, marked "not reviewed yet". The daily collection, the orchestrator's curation and the human's merge still decide what stays in `LESSONS.md` | A daily collection plus a human merge meant a lesson from a send-back during the build reached the other builders only the next day, too late to compound in a one-day build. Lessons come only from the tester's and reviewer's send-backs, and they are marked unreviewed, so a bad one can mislead for a day at most; the merge is still where one is dropped. Costs no model tokens, only a few prompt lines | `ops/dispatcher.sh` (`new_lessons`) |
| 22 | **All work traces back to the human. Any other ticket gets `needs-approval` and waits.** Work is a ticket the repo owner filed, or the orchestrator's split of one: the agents' account, a `Part of #N` line, the orchestrator's signature, and #N filed by the owner. A tester's bug, tech-debt, a split of a split, an orchestrator ticket without `Part of`, and any stranger's issue are held until the human removes the label. Lessons are read only from the agents' own comments | Two edges could make work without end: the tester filing new bugs, and triage splitting tickets again and again. The repo is public, so a stranger's issue or `Lesson:` comment would also have reached the agents. The check is plain code and fails closed: a ticket it can't trace waits for the human. Split once, so the plan becomes at most one level of tickets. Tested on 8 sample tickets on 2026-10-15 | `ops/dispatcher.sh` (section 0), `agents/orchestrator/SOUL.md` |
| 23 | **Conflicts and stale branches are handled by plain rules, and `main` only takes up-to-date PRs (`strict` on).** A PR that conflicts with `main` goes back to its owner to merge `origin/main` in (never rebase: no force-push), without counting as a send-back. A `needs-test` or `ready-to-merge` PR that fell behind gets `main` merged in by GitHub (`update-branch`) and goes round again | Agents run one at a time, but up to four PRs are open at once, cut from different points of `main`. Without this, a conflicting PR sat at `ready-to-merge` with nobody woken, and two PRs that each passed alone could break `main` together, which `ops/deploy.sh` would put live. Costs about one extra test and review per PR that falls behind. Tested on 7 sample PRs | `ops/dispatcher.sh` (section 0b), `ops/github-setup.sh` (`strict_required_status_checks_policy`) |
| 24 | **Handoff: the next agent starts as soon as the last one finishes.** Cron starts `dispatcher.sh --chain` every 2 minutes. It repeats the dispatcher while each run wakes an agent, up to 12 in a row | With one run per 5-minute tick, every handoff waited up to 5 minutes, and a PR's path (build, test, review) took 15 minutes of waiting alone. Cron stays for what no agent does: CI finishing, and the human's merges, approvals and labels. GitHub webhooks would need a public receiver and its secret on the VM; a 2-minute idle check costs about 4 GitHub API calls and no model tokens | `ops/dispatcher.sh` (`--chain`, `MAX_CHAIN`), `ops/setup-vm.sh` (cron line) |
| 25 | **`needs-human` has an exit: the human removes the label, and the item starts fresh.** The dispatcher notices the label go, resets the item's send-back and failed-run counts (the old counts are kept as `sendbacks/pr-N.before-<time>`), and the PR re-enters at its pipeline label, `changes-requested` by default. The human can swap that for `needs-test` or `needs-review` first. A human's comment overrules any agent's | Before, the third send-back removed `changes-requested`, so a released PR had no label and nobody woke; and its count stayed at 3, so putting the label back held it again at once. The human never writes the code, so the usual exit is a comment for the builder. Tested on 6 sample items | `ops/dispatcher.sh` (section 0) |
| 26 | **A ticket closes when its code works in main, not when its PR merges.** PRs say `Refs #N` (the dispatcher rewrites `Closes`, `Fixes`, `Resolves`). After each merge the dispatcher checks the merge commit in plain code: CI green on `main`, the VM deployed it and `scripts/install.sh` worked (`ops/deploy.sh` now writes `deploy-status.json`), and the public `/healthz` answers 200 once the app has it. Pass: it closes the ticket. Fail, or no result in 30 minutes: the ticket stays open (reopened if GitHub closed it) and its builder fixes it in a new PR. A `works-in-main` commit status records each result. The deploy cron now runs every 2 minutes | Before, nothing happened after a merge: CI on `main` and the deploy ran, but nobody read the result, and a ticket counted as done (unblocking the tickets that need it) even if it broke the live site. The orchestrator's "Needs are closed" now means "Needs work in main". Health and deploy get 10 minutes' grace for the service to come up. Tested on 9 sample states and 4 PR bodies | `ops/dispatcher.sh` (section 0c), `ops/deploy.sh` |
| 27 | **Agents can't make a change that can't be undone.** The agents' Linux user can't read or write the live data (OS permissions, checked), has no sudo, and can't push to `main`. The one way in is merged code that `scripts/install.sh` runs on the live database, so `SPEC.md` now requires a database backup before every install (newest 10 kept) and forbids deleting or rewriting saved runs and papers (schema changes only add). The reviewer checks both | A bad migration was the one path from an agent's work to lost data. The backup is product code, so the agents write it from the spec; nothing is added to `ops/` for it | `SPEC.md` (rule 8, Install), `agents/reviewer/SOUL.md` |
| 28 | **One ticket per piece of work.** Every failure on a ticket (CI, test, review, works in main) stays on it. A bug the tester finds outside its PR goes, as a comment, to the open ticket or open bug that owns that code; a new `bug` only when none does | So one UI button doesn't turn into many tickets, and its history stays in one place | `agents/tester/SOUL.md` (step 6) |
| 29 | **Lessons live in one pinned issue, as a checklist; no lessons PR, no daily orchestrator run.** The dispatcher adds each new `Lesson:` line (from the agents' account only) at once, unticked; the human ticks to keep or deletes to drop. Wake-up messages carry the ticked lessons and the newest 10 unticked ones. An edit by the agents' account that isn't the dispatcher's own is undone | A daily PR to change one text file was a manual merge every day, and a model run to write it. GitHub already gives the issue an editor with login and a history, so it needs no app UI or secrets. Tested on the VM: a fake ticked lesson added by the agents' account was removed in one run | `ops/dispatcher.sh` (section 0d), `ops/github-setup.sh` (creates issue #7) |
| 30 | **The orchestrator may approve the agents' own tickets, at most 3 a day; strangers' tickets only the human approves.** The dispatcher asks it once per ticket, with criteria in its prompt (a real gap against `SPEC.md`, not a duplicate, one PR in the product). Beyond the cap, or if it declines, the human decides. If the agents' account removes `needs-approval` when not asked, the label goes back on | Fewer manual steps, while the cap in plain code still stops a runaway loop. Tested on 6 sample cases | `ops/dispatcher.sh` (sections 0a and 5a), `APPROVALS_PER_DAY` |
| 31 | **The tester no longer re-runs the whole test suite; CI did it on the same commit.** It installs dependencies and runs single tests only when a check needs them, and spends its run on checks CI can't do (run twice → 0 new, failed fetch saved, the page) | The tester is only woken once CI passed on that commit, so its full-suite run repeated work and cost tokens | `agents/tester/SOUL.md` (step 3) |
| 32 | **`nemotron-3-ultra`'s context window in OpenClaw is 262,144, Ollama's real limit (was 1,048,576).** `gemma4:31b` stays at 131,072 although Ollama allows 262,144 | With 1M configured, OpenClaw wouldn't trim a long run's history before Ollama rejected it. A smaller window for the tester means less history re-sent on every turn | `agents/openclaw/openclaw.json5` |
| 33 | **Agents never read papers (WORKFLOW rule 11).** No PDFs, no arXiv pages, no live API calls; they work from a fixture with abstracts and authors cut out. The tester makes that fixture once by saving the query straight to a file and stripping it, checked by counts, never printed. `SPEC.md` also asks for 5 results sorted by submission date, and keeps only ID, version, title, PDF link and dates per paper | Paper text is the biggest token sink in this project and the app never needs it: it compares IDs and shows titles and links. Sorting by submission date keeps the 5 fresh (checked live on 2026-10-15: sorted by last update, 1 of 5 was a revision of a 6-day-old paper; by submission date, all 5 were new) | `agents/WORKFLOW.md` (rule 11), `agents/tester/SOUL.md` |
| 34 | **Each paper gets a one-sentence summary from `gemini-2.5-flash`, made by the app's daily job, not by an agent.** One request per run for all its new papers (30 s timeout); on any failure the page shows the abstract's first sentence, labelled "From the abstract:", and the run still succeeds. The key is `GEMINI_API_KEY` in `/home/app/.env` (mode 600, `app` only), copied by `infra/push-secrets.sh` from `secrets/app.env` | The human asked for summaries. A model sentence says what a paper does; an abstract's first sentence is often background. About 1.5k input tokens a day, one request, on the same free key as the reviewer. The build agents still never read abstracts (WORKFLOW rule 11): tests use a fake summarizer and made-up abstracts. The app's Ollama key turned out to be the agents' own, so it gave no separation | `SPEC.md` rules 18–20, `secrets/app.env` |
| 35 | **The page and the code layout are in `SPEC.md`: the page as words and a text sketch (rules 21–26), the code as a table of files per lane with fixed touch points (Code layout).** The orchestrator splits along it and copies Files likely touched from it | The human approved the look from a mockup built outside the repo (`experiments/`, real arXiv data and real summaries); the mockup's HTML is not given to the agents, so all product code stays theirs. Fixed function names and file owners let three builders work at once without waiting or colliding, and `requirements.txt` has one owner. Day arrows and a date picker need no JavaScript; history is capped at 10 on the page, 50 per page on `/runs` | `SPEC.md` (Page layout, Code layout), `agents/orchestrator/SOUL.md`, `agents/*/IDENTITY.md` |
| 36 | **Backend rules in `SPEC.md` (27–32):** Run now starts the run as its own process after one transaction that checks the rate limit and saves the run; one run at a time behind a lock file; a visible "run in progress" that reloads itself (no JavaScript) and times out at 15 minutes; one database connection per request with WAL, foreign keys, a 5 s busy timeout and indexes; gunicorn 2 workers and 60 s timeout; logs in `/var/log/daily-briefing/` with rotation | A run can take 10–45 s (dates 3 s apart, plus a 30 s model timeout), longer than gunicorn's default 30 s worker limit, and the schedule and Run now could overlap. | 37 | **How three builders' work fits together.** The spec now names the job's write functions too, and every lane's tests fill test databases only through them. A builder that needs something another lane hasn't built files `Needed by #N: …` (it goes through the usual approval), labels its ticket `blocked` (the dispatcher skips it) and stops; the orchestrator assigns the request to the right lane first and gives #N back once it's closed. The reviewer rejects a change to a touch point or a file outside the lane. A last tester ticket tests the lanes together | Without named write functions, builder-web's tests would need SQL of their own; without a blocked path, "say so in the PR" led nowhere; a silently renamed function breaks the other lane only after both merge | `SPEC.md` (Code layout), `agents/builder/SOUL.md`, `agents/orchestrator/SOUL.md`, `agents/reviewer/SOUL.md`, `ops/dispatcher.sh` |
| 38 | **v1 spec is bare-bones: the brief's core and what the agent graph needs, nothing more.** One request per run for the 5 newest `cs.MA` submissions, every run saved, new by stable ID, a page with the latest briefing (S.No, Title, DOI, PDF), the history and Run now, `/healthz`, install and tests. Per-date briefings from Oct 13, AI summaries, day navigation, background runs and the full mockup look moved to `roadmap.md`, each to come back as a change request | The full spec (340 lines, 32 rules) would have split into 10+ tickets and cost the orchestrator and every builder more context; the brief says a small core the agents shipped beats a long feature list. | 39 | **CI gates review for every PR, including the tester's own.** The reviewer section waits while CI runs and sends a red PR back (counted against CI), as the tester section does for builder PRs | Found by an audit of the live VM on 2026-10-15: the tester's own PRs skip the tester step and so reached the reviewer without the CI check; the merge was still blocked by the required `pytest` check, but the reviewer could spend a run on red code. | 40 | **WORKFLOW.md tells the OpenClaw agents how `exec` works in allowlist mode:** no redirections or heredocs, no `$(…)`, no `cd`, `python3` or `.venv/bin/python` only; write files with the `write` tool | The first build run (builder-ingest, #9, 2026-10-16) lost turns to three denials: `python - <<'PY'`, `.venv/bin/python - <<'PY'` and `cd …/repo && gh issue view 9 … 2>&1`. ## Infra: move to AWS (2026-10-14)

| # | Decision | Why | To change |
|---|---|---|---|
| 6 | **The VM runs on the AWS Free plan, not Oracle Always Free** | Oracle's only Always Free Arm shape returned "Out of host capacity" on all 42 tries over ~6 hours (6 at 2 OCPU / 12 GB, 36 at 1 / 6). `us-sanjose-1` has one availability domain, so there was nowhere else to try. The brief names the AWS Free plan as plan B. We switched after hours rather than the brief's "a day" to protect the 5-day schedule. The account's credits last until 2027-01-02 | The Oracle Terraform is in git history (commit `1ee3b1b`) |
| 7 | **VM size: `m7i-flex.large`** (2 vCPU / 8 GB, x86) | The size the brief names for plan B, and on the Free plan's instance list. About $2.50/day of credits, so they cover the build week and the review week | `instance_type` in `infra/terraform.tfvars`. A stop and start resizes it (a new public IP; DuckDNS follows). `t3.small` makes credits last ~4x longer |
| 8 | **Own VPC, not the account's default VPC** | Works the same in any account, including one whose default VPC was deleted | `infra/main.tf` |
| 9 | **No Elastic IP.** The VM keeps the public IP it boots with | Attaching one after boot changes the IP while first boot is still downloading packages. A reboot keeps the IP; only a stop and start changes it, and the DuckDNS cron follows within 5 minutes | Add an `aws_eip` in `infra/main.tf` |
